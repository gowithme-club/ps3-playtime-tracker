# gwm-stats-ps3

VSH-плагин для PS3 (CFW / PS3HEN), который определяет запущенную игру и отправляет
статистику игры на [gowithme.club](https://gowithme.club/). Никаких вторых устройств:
плагин живёт на самой консоли и шлёт данные сам.

Цель — распространяемый в комьюнити пакет: поставил PKG, вписал токен, играешь.

**Ставить на свою консоль** — [docs/QUICKSTART.md](QUICKSTART.md): короткая
инструкция для тех, кто пришёл со стороны и не собирается читать остальное.
Дальше в этом файле — устройство, замеры и решения, то есть материал для того,
кто плагин дорабатывает.

## Семейство репозиториев

Этот плагин — один из клиентов gwm-stats. Вся доменная логика (дедуп, сессии,
трофеи, live-статус, дашборд) живёт на сервере; клиент только шлёт события по
ingest API.

| Репозиторий | Роль |
| --- | --- |
| gwm-stats | сервер и контракт ingest: `docs/ingest-api-v1.md`, для авторов клиентов — `docs/ingest-api-v1-client.md` |
| **ps3-playtime-tracker** (этот репозиторий) | клиент: VSH-плагин для PS3 (CFW / PS3HEN) |
| [switch-playtime-tracker](https://github.com/gowithme-club/switch-playtime-tracker) | клиент: Atmosphere-sysmodule для прошитой Switch, тот же ingest |
| gwm-stats-ios | приложение для iOS: читает публичный API сервера, в ingest не пишет |

Изменение серверного поведения или самого контракта — в gwm-stats, не здесь.
Switch-клиент решает те же задачи на другой консоли: если вопрос про поведение
ingest (дедуп, watermark, формат тел), полезно сверяться с ним.

## Как это устроено

PS3 не умеет держать фоновые homebrew-процессы: при старте игры XMB выгружает приложение.
Резидентно живёт только VSH-плагин — `.sprx`, который грузится в процесс `vsh.self`
на этапе загрузки системы (так работает webMAN MOD). Поэтому продукт — именно плагин.

```
vsh.self
 └── gwm.sprx           резидентный плагин
      ├── детект игры         game_plugin → gameInfo, опрос раз в 10 секунд
      ├── сессии              закрытая сессия = startedAt + endedAt + seconds
      ├── трофеи              TROPUSR.DAT профиля, stat каждый цикл, разбор при изменении
      ├── очередь             /dev_hdd0/tmp/gwm/queue.jsonl — переживает офлайн и выключение
      ├── снимок сессии       /dev_hdd0/tmp/gwm/open.jsonl — открытая сессия, каждый цикл
      └── отправка            heartbeat раз в минуту + сессии по закрытию + трофеи,
                              Authorization: Bearer из gwm.cfg
```

Плагин намеренно не зависит от webMAN, IRISMAN и прочего — он самодостаточен и может
стоять рядом с ними.

## Статус

Клиент работает целиком: собирается на Apple Silicon, грузится в XMB, определяет
игру, копит сессии, читает выбитые трофеи и отправляет всё это на сервер.

Проверено на живой консоли (4.92 HFW, PS3HEN 3.5.0) против заглушки сервера
(`tools/mock_ingest.py`), реализующей контракт `docs/ingest-api-v1-client.md`:

```
POST /ingest/v1/heartbeat   раз в 60 секунд, ровно по расписанию
  {"sentAt":"2026-08-16T21:45:45Z","current":[{"account":"SamplePlayer",
   "titleId":"BLES00951","titleName":"DRIVER Сан-Франциско",
   "platform":"ps3","startedAt":"2026-08-16T21:43:55Z"}]}

POST /ingest/v1/sessions    через 10 секунд после выхода из игры
  {"sessions":[{... "startedAt":"...21:43:55Z","endedAt":"...21:47:55Z",
   "seconds":240}]}

POST /ingest/v1/trophies    при изменении TROPUSR.DAT, проход при загрузке
  {"account":"SamplePlayer","platform":"ps3","setId":"NPWR00331_00",
   "trophies":[{"id":1,"earnedAt":"2026-08-16T21:31:22Z"},
               {"id":26,"earnedAt":"2026-08-16T21:41:12Z"}, ...]}
```

`endedAt − startedAt` совпадает с `seconds` — подсчёт по тикам RTC и метки
времени сходятся независимо. Очередь на диске очищается после `200`.

Поле `account` во всех трёх запросах — имя локального профиля консоли, и берут
его все три из одного места: явное значение из `gwm.cfg`, если задано, иначе
`localusername` того профиля, чьи данные отправляются. Это не мелочь: ключ
дедупа на сервере включает `account`, и разъехавшиеся имена дали бы двух разных
людей — сессии за одним, трофеи за другим.

Трофеи сверены с файлом на HDD: те же шесть выбитых из пятидесяти одного,
времена совпадают с точностью до поправки часов — консоль спешит на минуту,
и на минуту же сдвинуты все `earnedAt`.

Сделано с тех пор:

- **боевой сервер отвечает.** `POST /ingest/v1/heartbeat` и
  `/ingest/v1/trophies` на gowithme.club принимают данные с боевым токеном
  и отвечают `200`. Заглушка больше не единственный приёмник;
- **автозагрузка работает и включается сама.** С 0.10.26 плагин дописывает
  себя в `autoexec.bat` после первого ответа `200` — руками системный файл
  править больше не нужно, разбор решения в «Автозагрузке» ниже. Проверено
  на живой консоли: строка убрана, плагин загружен через `loadprx`, файл стал
  побайтово тем, что ожидает хостовый тест; следующая перезагрузка подняла
  плагин уже из этого файла и второй раз он в него не полез. В
  `boot_plugins.txt` плагин теперь не переедет — см. там же, почему;
- **плагин стало видно снаружи.** `/dev_hdd0/tmp/gwm/status.txt` — состояние
  плагина парами «ключ = значение», переписывается каждый цикл. До него
  плагин, ушедший на боевой сервер, не оставлял на консоли ни следа;
- **экран состояния** — homebrew в `app/`, читает тот же файл и рисует его
  на телевизоре. Собирается открытым тулчейном: `make -C app pkg`.
  **На консоли пока не запускается**: пакет ставится, процесс создаётся,
  но до `main()` дело не доходит — чёрный экран и возврат в XMB.
  Что проверено и чем доказано — в [app-pkg-debug.md](app-pkg-debug.md).

Осталось до раздачи комьюнити — на первых двух пунктах инструкция для новичка
обрывается буквально:

1. **скачать нечего.** Релизов у репозитория нет, `/dist/` в `.gitignore`,
   а CI не будет: SDK проприетарный. Пока подписанная сборка не выложена
   в GitHub Releases, шаг «скачать плагин» ведёт на пустую страницу;
2. **токен выдаётся руками**, самообслуживания на сервере нет, и в
   [QUICKSTART.md](QUICKSTART.md) на месте канала связи стоит заглушка;
3. установочный PKG для самого плагина и ввод токена без FTP — сейчас
   `gwm.cfg` правится руками. Правка автозагрузки из установки уже ушла,
   это последнее место, где нужен компьютер;
4. **запуск экрана состояния на консоли** — приложение не доходит
   до `main()`, см. [app-pkg-debug.md](app-pkg-debug.md). Пока это
   не решено, остальное про экран смысла не имеет;
5. кириллица в экране состояния: подписи пока латиницей, отрисовка
   UTF-8 через FreeType в NoRSX не проверена.

## Что уходит на сервер

Реализованы три ручки из четырёх:

- `POST /ingest/v1/heartbeat` — раз в 60 секунд, с пустым `current[]`, когда
  никто не играет;
- `POST /ingest/v1/sessions` — батч закрытых сессий сразу после выхода из игры
  и повторные попытки, пока сервер не подтвердит;
- `POST /ingest/v1/trophies` — полное состояние одного трофейного сета.
  Каждый десятисекундный цикл опроса плагин делает `stat` по всем сетам
  профиля и сравнивает пару (размер, `mtime`) с той, что была при последнем
  разборе. Пока ничего не менялось, круг не стоит ни одного чтения и ни
  одного запроса; изменившийся сет разбирается и отправляется — по одному за
  цикл, потому что полный разбор разом ослепил бы детект игры на минуту с
  лишним. Выбитый трофей уезжает примерно за десять секунд.

  Отметки живут в памяти, так что после загрузки плагина все сеты
  разбираются заново — это и есть тот полный проход, который забирает
  трофеи, выбитые пока плагин не работал.

  Поля `title` в теле нет: соответствие сета игре плагину неизвестно,
  а названия сервер дообогащает через PSN по `setId`.

## Что будет на сервере сразу после установки

Вопрос, который задают первым: подтянется ли всё, во что человек играл до
установки плагина. Ответ разный для трофеев и для наигранного времени.

**Трофеи подтянутся полностью.** Время получения хранится в самом
`TROPUSR.DAT`, поэтому трофей, выбитый год назад, уедет с прошлогодним
`earnedAt`. Проход по всем сетам делается при каждой загрузке плагина, так что
специального режима «первая установка» не нужно.

Спамить в Telegram годовым бэклогом при этом не придётся, но не из-за флага
`firstSeed` в ответе — он лишь сообщает клиенту, что засев был первым. Анонсы
отсекаются сравнением времён: в очередь уведомлений попадает только то, у чего
`earnedAt` новее момента прихода первого сета этого аккаунта. Отсюда полезное
для нас следствие — порядок сетов и паузы между ними ни на что не влияют,
и разбивать проход на «сначала один сет, потом остальные» смысла нет.

**Истории сессий не будет — её неоткуда взять.** PS3 не ведёт учёт
наигранного, это появилось только на PS4. Проверено на живой консоли, а не
по документации:

| где могло бы лежать | что там на самом деле |
|---|---|
| `/dev_hdd0/vsh/` | `rtcalarm.dat`, `task.dat`, `pushlist` — про игры ничего |
| `etc/boot_history.dat` | 32 байта, один `titleId` последней игры, без времени |
| `savedata/<TITLEID>/` | только mtime каталога: «заходил примерно тогда-то» |

Косвенные источники (mtime сейвов, времена трофеев) дают моменты, но не
длительности. Складывать выдуманные длительности рядом с измеренными сессиями
мы не будем: дашборд перестанет отличать данные от догадок. Часы считаются
со дня установки — так же, как PSN показывает трофеи с историей, а время
начинает считать с момента подключения.

**Трофеи читаются только у активного профиля.** На консоли с несколькими
профилями (у автора их четыре, 83 сета суммарно) плагин не лезет в чужие
каталоги. Обход берёт текущего пользователя на каждом шаге, поэтому смена
профиля переключает и трофеи: со временем на сервер попадут все, кто реально
играет, а не все, кто когда-либо заводил профиль.

## Как клиент понимает, что уже доставлено

`GET /ingest/v1/sync` и дозаливка по watermark **намеренно не реализованы**.
Ими пользоваться — значит разбирать JSON из ответа и сравнивать даты, то есть
тащить в плагин парсер там, где сейчас только сборщик строк. Надобности нет:
источник истины — файл очереди на HDD, строка удаляется только после `200`,
а сервер идемпотентен. Watermark нужен для восстановления после потери
локального состояния, но если у нас пропал файл на диске, восстанавливать
нечего. Клиент смотрит только на HTTP-код, тело ответа не разбирая.

Обращение с кодами: `200` — строки уходят из очереди; `400` и `413` — батч тоже
выбрасывается, он не станет валиднее, а вечный ретрай заклинил бы очередь;
`401`, `429`, `5xx` и сетевые ошибки — очередь сохраняется до следующей попытки.

## Неделя без сети

Консоль вполне может месяц простоять на даче без интернета, и весь этот улов
обязан доехать целым. Очередь на HDD для того и сделана, но одного файла мало —
есть две вещи, которые в офлайне ломаются неочевидно.

**Время.** Поправка часов приходит с заголовком `Date`, то есть только вместе
с ответом сервера. Без сети её взять неоткуда. Поэтому в очередь пишется
**сырое время консоли**, а поправка добавляется при отправке — когда она уже
известна. Метка имеет фиксированную ширину, так что сдвиг делается прямо
в буфере, без пересборки строки и без разбора JSON.

Разница не косметическая: на консоли с живой батарейкой речь про минуту,
а на консоли с севшей CR2032 — это обычная болезнь PS3 — часы сбрасываются
при каждом отключении питания, и весь улов уехал бы с датами из двухтысячных.
Случай «часы прыгнули, пока консоль стояла без сети» не лечится ничем: такой
информации на консоли просто нет.

Проверено на живой консоли: в очередь подложена сессия с метками `23:00:00` и
`23:05:00`, на сервер уехало `22:59:00` и `23:04:00` — ровно поправка часов,
`seconds` не тронуты (длительность считается разностью тиков, а не дат),
остальная строка байт в байт та же.

**Рост очереди.** Потолок в 512 КБ — это порядка двух с половиной тысяч
сессий, то есть годы игры. Упереться в него можно, только если отправка
сломана насовсем. Дойдя до потолка, очередь перестаёт принимать новое,
а не выбрасывает старое: накопленное уже пережило выключения консоли
и заслуживает доставки больше, чем очередная строка.

## Выключение посреди игры

Сессия попадает в очередь при выходе из игры в XMB. Консоль же часто
выключают прямо из игры, и тогда перехода плагин не застаёт: сессия жила
только в памяти и пропадала целиком. На сервере такие вечера выглядели
странно — трофеи за день есть, наигранного времени нет. Сервер видит их
лишь по live-статусу, который гаснет через пять минут тишины, и сохранять
из него сессию не берётся: он не знает, придёт ли настоящая позже.

С 0.10.28 открытая сессия каждым циклом опроса пишется в
`/dev_hdd0/tmp/gwm/open.jsonl` — готовой строкой очереди, закрытой «сейчас»
(`plugin/checkpoint.h`). Обычное закрытие файл удаляет. Если при загрузке
плагина файл на месте, прошлый запуск кончился посреди игры, и строка уходит
в очередь с концом на последнем снимке. Потеря — не больше десяти секунд,
а длительность по-прежнему измерена консолью, а не выдумана.

**Время.** Снимок, в отличие от очереди, перезагрузку переживает всегда.
На консоли с севшей CR2032 часы при этом сбрасываются, и сырые метки прошлого
запуска к поправке нового отношения не имеют. Поэтому снимок пишется уже
исправленным временем (первый байт `c`), если поправка в том запуске была
выучена, иначе сырым (`r`). Восстановление идёт после первого heartbeat и
переводит исправленную строку в сырое время нового запуска — отправка
добавит поправку обратно, и на сервер уйдут ровно те метки, что были
в снимке. Если сеть в новом запуске ещё не поднялась, строка ложится
как есть, и ошибка равна разнице поправок — на живых часах это секунды.

**Обрыв записи.** Снимок пишется через временный файл; восстановление читает
временный, если основного нет или он битый, а строку без закрывающей скобки
и перевода строки отбрасывает. Снимок удаляется после записи сессии
в очередь, не до: пропавшее между ними питание даст строку дважды с одним
`startedAt`, а такой дубль сервер отбрасывает по уникальному индексу.

Выгрузка плагина посреди игры (`unloadprx`) снимок тоже оставляет: при
следующей загрузке сессия закроется на последнем снимке, а если игра всё ещё
идёт, начнётся новая.

## Подпись

Плагин подписывается `scetool` с теми же параметрами, что webMAN использует
для своих vsh-плагинов (key revision `0A`, auth-id `1070000052000001`).

Готовый `scetool.exe` из репозитория webMAN не годится: он собран под Cygwin
и требует `cygwin1.dll` и `cygz.dll`, которых там нет. Поэтому
`scripts/get-signing-tools.sh` собирает scetool из исходников — они
самодостаточны (свои aes, sha1, ec, ecdsa), из внешнего нужен только zlib.
Собирается нативно на macOS arm64, то есть подпись идёт быстро и без wine:

```bash
make signing-tools
```

Ключи и кривые берутся из webMAN и лежат в `vendor/`, который в `.gitignore` —
плодить ещё одну публичную копию консольных ключей ни к чему.

Итого сборка разнесена: компиляция в виртуалке (нужен win32-компилятор SDK),
подпись — на хосте.

## Сборка

Открытый тулчейн ставится одной командой, из готовых nightly-сборок
[ps3dev/ps3dev](https://github.com/ps3dev/ps3dev) — компилировать gcc из исходников
не нужно. Есть нативные сборки под macOS arm64/x64 и Linux x64.

```bash
make toolchain     # в ~/ps3dev, или PS3DEV=/opt/ps3dev make toolchain
make tools-check   # что установилось
```

Для тех, кто не хочет ставить тулчейн в систему, есть `make docker-toolchain`
(`docker/Dockerfile`). На Apple Silicon это эмуляция amd64 и заметно медленнее.

### Почему одного PSL1GHT не хватит

Проверено на установленном тулчейне, а не по документации:

| нужно для PRX | есть в ps3dev |
|---|---|
| `ppu-gcc -mprx` | нет, `unrecognized command line option` |
| prx-стартапы `ecrti.o` / `ecrtn.o` | нет |
| `ppu-lv2-prx-exportpickup` | нет |
| vsh/paf export-стабы | нет |
| формат `ET_SCE_PPURELEXEC` в binutils | нет, только `elf64-powerpc` |

`sprxlinker` из PSL1GHT ситуацию не спасает — вопреки названию, PRX-модуль он не
порождает. По исходнику: он берёт готовый homebrew-ELF, ставит
`e_ident[EI_OSABI] = ELFOSABI_CELLLV2`, требует секцию `.sys_proc_prx_param`, чинит
счётчики импортов в `.lib.stub` и записи `.opd`. Это сторона *потребителя* системных
PRX, а не сторона модуля.

Патч `binutils-2.22-PS3.patch` из ps3toolchain тоже ничего не добавляет: 90 строк,
трогают только SPU-эмуляцию линкера, слов `prx`/`SCE` в нём нет.

Раскладка в самом webMAN подтверждает границу — из 18 его подпроектов PSL1GHT собирает
только обычные приложения (`reloadxmb`, `load_wmm`, `pkglaunch`, `prepISO`, `updater`),
а всё резидентное (`vsh_menu`, `wm_proxy`, `ps3mon`, `slaunch`, `video_rec`) и lv2-пейлоады
(`netiso`, `rawseciso`) — только Cell SDK.

Поэтому в проекте два тулчейна:

- **PSL1GHT** — установочный PKG и homebrew-конфигуратор для ввода токена;
- **Cell SDK** — сам `gwm.sprx`, подключается через `CELL_SDK`.

Cell SDK нужен **только билд-машине**: код в проприетарные библиотеки не линкуется,
vsh-функции резолвятся в рантайме по NID (см. ниже), в бинарь зависимость не тянется.

### Cell SDK

В репозиторий он не входит и входить не может. Из офлайн-установщика 4.75 нужны
три пакета из `InstallFiles`, остальные ~7 ГБ — документация, апдейтеры девкитов
и сэмплы:

| пакет | что оттуда нужно |
|---|---|
| `PS3_Toolchain_411-Win_420_001.zip` | `ppu-lv2-gcc` 4.1.1, `ppu-lv2-ld`, `ecrti.o`/`ecrtn.o` |
| `PS3_SDK-475_001.zip` | `cell/target` — заголовки и библиотеки; `cell/host-win32/bin` — `ppu-lv2-prx-libgen`, `ppu-lv2-prx-strip`, `make_fself` |
| `PS3_SDK_Samples-475_001.zip` | `cell/samples/mk/*` — система сборки |

```bash
unzip -q PS3_Toolchain_411-Win_420_001.zip -d ~/ps3sdk
unzip -q PS3_SDK-475_001.zip              -d ~/ps3sdk 'cell/target/*' 'cell/host-win32/*'
unzip -q PS3_SDK_Samples-475_001.zip      -d ~/ps3sdk 'cell/samples/mk/*'
```

Получается ~200 МБ в `~/ps3sdk/cell`. Без второго пакета сборка падает дважды:
сначала на отсутствующем `sys/prx.h`, потом на `ppu-lv2-prx-libgen`.

### Билд-хост: нужен настоящий x86

Хостовые бинарники SDK существуют только под win32 (`PE32 i386`), сборок под Linux
и macOS в установщике нет, хотя система сборки их и предусматривает
(`sdk.makedef.mk` выбирает `host-linux` по `uname`).

У `ppu-lv2-gcc.exe` вырезаны релокации, то есть он обязан грузиться строго по
`ImageBase=0x400000`. **Под user-mode эмуляцией это не работает**: Rosetta и
qemu-user живут в одном адресном пространстве с программой и занимают этот адрес,
wine падает с `STATUS_CONFLICTING_ADDRESSES` (`c0000018`). Проверено и закрыто:

| подход | результат |
|---|---|
| amd64-контейнер, wine64 | нет `syswow64/ntdll.dll` — 32-битный PE не стартует |
| amd64-контейнер + `wine32:i386` | библиотеки на месте, всё равно `c0000018` |
| i386-контейнер (`linux/386`) | `c0000018` |
| `WINEPRELOADRESERVE`, `setarch -R`, `WINEARCH=win32` | не помогают |

**Решается полноценной виртуалкой.** В x86_64-VM гостевое ядро распоряжается
адресным пространством само, коллизии нет, и на Apple Silicon всё собирается:

```bash
brew install colima qemu lima-additional-guestagents
make vm     # поднять стенд (первый запуск долгий: это эмуляция)
make sprx   # собрать плагин
```

`scripts/vm-setup.sh` ставит wine в виртуалку и готовит SDK. Две неочевидные
детали, без которых сборка не идёт:

- **регистр путей.** Wine отдаёт пути в нижнем регистре (`z:/users/...`), а Linux
  регистрозависим — компилятор не находит даже собственный `stddef.h`.
  Лечится ссылкой `/users -> /Users`.
- **WINEPATH.** `ppu-lv2-gcc` ищет свои утилиты (`ppu-lv2-prx-libgen` и прочие)
  по виндовому `PATH` внутри wine, а не по `PATH` хоста.

На настоящем x86_64 Linux виртуалка не нужна — там достаточно
`docker/Dockerfile.cellsdk` и `make sdk-image`.

В публичный CI сборка не выносится: SDK проприетарный, класть его в GitHub Actions
нельзя. Релизные PKG собирает мейнтейнер у себя, комьюнити получает готовый файл.

### Особенности линковки

Из офлайн-установщика собрать удаётся не «как у webMAN» — часть инструментов
Sony в него не входит:

- спеки gcc по умолчанию зовут `--alternative-ld=ps3ppuld`, линкер SN Systems
  из ProDG. Его нет ни в одном пакете установщика, включая `SNCPPUToolchain`.
  Ключ `-mno-sn-ld` переключает на GNU-линкер `ppu-lv2-ld`, который есть;
- `--strip-unused-data` из makefile webMAN — опция того же линкера SN,
  GNU-линкер её не знает. Обходимся без неё, ценой чуть большего размера.

### vsh-стабы и лицензия

`libvsh_export_stub.a`, `libpaf_export_stub.a`, `libvshmain_export_stub.a` и прочие —
**не из SDK Sony**, их там нет вообще. Это работа сцены, они лежат в репозитории
webMAN MOD, в каталоге `lib/`. Оттуда же берутся `scetool` и ключи для подписи.

Следствие: webMAN MOD распространяется под **GPLv3**, поэтому и этот проект — GPLv3.
Для плагина, который планируется раздавать комьюнити, это нормально, но выбора здесь
нет: и стабы, и приём с резолвом по NID взяты оттуда.

## Каркас модуля: чем оплачен один физический ребут

`module_start` у vsh-плагина исполняется **как поток** внутри vsh и обязан
завершить себя явно. Если просто вернуть значение — XMB виснет намертво,
причём мгновенно, ещё на загрузке модуля. Проверено на живой консоли: webMAN
и FTP умерли, ping отвечал, помогло только выключение по питанию.

Правильно так (буквально как в `wm_vsh_menu`):

```c
int gwm_start(uint64_t arg)
{
    sys_ppu_thread_create(&tid, thread, arg, -0x1d8, 0x2000, 1, "name");
    _sys_ppu_thread_exit(0);      // без этой строки консоль зависает
    return SYS_PRX_RESIDENT;
}
```

Из того же ряда, всё обязательно:

- сигнатура старта — `(uint64_t arg)`, а не `(size_t, void *)`;
- `_sys_ppu_thread_exit` — это прямой сисколл 41, в заголовках SDK его нет;
- остановка делает работу в отдельном потоке, джойнит его, затем
  `finalize_module()` (сисколл 482) и снова `_sys_ppu_thread_exit(0)`.

### Стек рабочего потока: ещё один ребут

Второе зависание — на первом же вызове `gameInfo`. Причина в размере стека:
поток был создан с `0x2000` (8 КБ), как у `vsh_menu`. Но его поток рисует
оверлей, а `View_Find` → `plugin_GetInterface` → `gameInfo` уходит вглубь `paf`.
webMAN на тот же самый вызов отводит своему `poll_thread` **48 КБ**
(`THREAD_STACK_SIZE_POLL_THREAD`) и приоритет `0xA00` (`THREAD_PRIO_POLL`).

Симптом характерный: сборка, показывающая только уведомление, работает
(`vshtask_notify` — мелкий вызов), а сборка с детектом убивает XMB мгновенно.
Если плагин виснет там, где начинает трогать vsh-интерфейсы, — смотреть надо
на стек, а не на логику.

Ориентир простой: брать параметры потока у той функции webMAN, которая делает
то же самое, а не у первого попавшегося плагина.

## Как плагин достаёт название игры

Референс — webMAN. Два независимых пути, оба без линковки с Sony-стабами:

1. **Через vsh (основной).** `getNIDfunc` идёт по таблице экспортов vsh от
   `*(u32*)0x1008C + 0x984`, находит `View_Find` и `plugin_GetInterface` в модуле `paf`
   (NID `0xF21655F3` и `0x23AFB290`), затем `View_Find("game_plugin")` →
   `gameInfo(buf)`, где `buf+0x04` — Title ID, `buf+0x14` — название.
2. **Через syscall 8 (запасной).** Опкод PS3MAPI `0x7777`, команды `0x0021`
   (`GET_ALL_PROC_PID`) и `0x0022` (`GET_PROC_NAME_BY_PID`) дают pid и путь к EBOOT,
   из которого вынимается Title ID; название — из `PARAM.SFO`. Требует Cobra/Mamba/HEN.

Путь 1 сразу отдаёт и ID, и человекочитаемое название, поэтому он основной,
а путь 2 — фолбэк, если интерфейс `game_plugin` недоступен.

## Что плагин говорит в XMB

Уведомления идут в системный тост в правом верхнем углу — `vshtask_notify`
(NID `0xA02D46E7`), тот же вызов, которым представляется webMAN на загрузке.
Сообщения двухстрочные: первая строка — что произошло, вторая — чем кончилось.

Поведение тоста измерено на консоли 18.08.2026 линейкой из ста символов
(4.92 HFW, PS3HEN 3.5.0):

- **`\n` переносит строку** — коробка растёт в высоту под содержимое;
- **строка ломается сама на 28 символах**, по пробелу, если он есть, и
  вразрез слова, если нет. Двухстрочная заставка webMAN на загрузке — это
  та же укладка, а не его собственный перенос;
- **обрезки нет** по крайней мере до ста символов: линейка доехала до конца,
  уложившись в четыре строки. Резать название игры, как это делает
  PS3PlaytimeTracker (40 символов), не требуется.

Проверять формат, не тратя перезагрузку на каждую попытку, можно снимком
экрана через webMAN. Собственной команды
показать произвольный текст у webMAN нет: `notify.ps3` рисует своё
«notify.ps3 : OK» и сообщение из запроса не берёт.

```
gwm-stats 0.10.21 loaded: SamplePlayer     при загрузке плагина
gwm-stats hb: 200                          первый heartbeat и часы
gwm-stats: Demon's Souls                   сессия закрыта: человек уже
Session 47 min, sent                       в XMB и уведомление увидит
gwm-stats: trophies                        набор трофеев уехал
Sent to server
```

Коды печатаются словом и числом сразу — `bad token (401)`, `no connect (-3)`:
слово нужно человеку у телевизора, число — когда он придёт с этим в issue.
Собственные коды транспорта занимают весь диапазон -1..-6 (`http.h`), так что
переводятся без остатка; из ответов сервера названы те, где число само по себе
ничего не объясняет.

Разница между «queued» и «dropped» не косметическая: `400` и `413` очищают
очередь (см. `upload.h`), то есть данных больше нет нигде, а всё остальное
осталось на диске и уедет позже.

**Сообщение о сессии показывается не сразу, а следующим циклом опроса**, плюс
секунда сверху. Показ в момент закрытия сессии проигрывает гонку с чёрной
заставкой перехода игра→XMB: тост уходит в неё и пропадает незамеченным.
Проверено на консоли 18.08.2026 — сессия уезжала на сервер с кодом `200`,
а на экране не появлялось ничего. Тем же кончилось у PS3PlaytimeTracker,
где уведомление точно так же кладётся в буфер и выстреливает циклом позже.

Три вещи, которых здесь намеренно нет:

- **уведомления о каждом выбитом трофее.** XMB показывает свой попап сам,
  а наш дублировал бы его поверх геймплея. Плюс сказать нам нечего: имён
  трофеев в `TROPUSR.DAT` нет — только числовые id, — и какой игре
  принадлежит набор, знает лишь сервер, поэтому `setId` в уведомление
  не идёт;
- **сообщений до конца первого круга по трофеям.** Отметки `trophy_cache`
  живут в памяти, и после каждой загрузки плагин заново отправляет все
  наборы — по одному за цикл. На четырёх десятках сетов это попап каждые
  десять секунд минут на семь, и ни один из них не про свежий трофей.
  Уведомления включаются, когда круг прошёл вхолостую: дальше отправка
  набора означает, что он изменился;
- **повторов одного отказа.** Неотмеченный набор пробуется снова раз
  в минуту, и при протухшем токене попап шёл бы всю игровую сессию.
  Показывается первый отказ в серии, дальше тишина до успеха.

Тексты собираются в `plugin/msg.h` отдельно от vsh и проверяются
`tests/msg_test.c`: сообщение читает человек у телевизора, а проверка формата
на консоли стоит перезагрузки.

## Автозагрузка: плагин прописывается сам

Строка в `/dev_hdd0/autoexec.bat` была единственным пунктом установки, где
человеку приходилось править системный файл руками — с виндовыми переводами
строк и оглядкой на чужие плагины, которые там уже живут. Плагин работает
внутри vsh и до этого файла дотягивается сам, так что с 0.10.26 дописывает
себя туда самостоятельно (`plugin/autostart.h`).

Три правила, из которых следует всё остальное:

- **прописываемся только после подтверждённой работы** — после первого ответа
  `200` от сервера. К этому моменту доказано, что плагин поднялся, токен
  верный и сеть есть. Прописаться раньше значило бы поднимать при каждой
  загрузке консоли модуль, о котором ничего не известно, — а в худшем случае
  роняющий XMB;
- **чужое не трогаем.** Своя строка дописывается в конец, к уже имеющимся,
  а не вместо них. Если своя строка уже есть — не делается ничего, сколько
  бы раз плагин ни перезапускался. Строку, закомментированную руками, плагин
  тоже считает своей и не воскрешает: убрал человек её осознанно;
- **не понимаем — не трогаем.** Файл, который не поместился в буфер целиком,
  не переписывается вовсе: лучше не прописаться и оставить это человеку, чем
  обрезать чужую автозагрузку по границе буфера.

Если в файле ещё нет `wait xmb`, пишется полный блок с ожиданием: без него
команда может выполниться раньше, чем XMB готов, а ранняя загрузка плагина
роняет консоль. Если ожидание уже есть — добавляется только `wait 3`, чтобы
две загрузки не шли вплотную. Запись идёт через временный файл с
переименованием, как в `queue.h`.

Сборка нового содержимого отделена от файловых операций и проверяется
`tests/autostart_test.c`: файл принадлежит не нам, и ошибка стоила бы человеку
автозагрузки целиком — такое нельзя проверять на живой консоли впервые.

**Что измерено на консоли 18 августа 2026.** Своя строка убрана из
`autoexec.bat` руками, плагин загружен через `loadprx` на устоявшемся XMB.
После первого ответа `200` файл стал побайтово тем, что ожидает хостовый
тест — 124 байта: чужой `playtime_mk` на месте, `wait 3` между двумя
загрузками, CRLF. Временный `autoexec.gwm` не остался, то есть запись прошла
переименованием, а не резервной ветвью. Следующая перезагрузка подняла плагин
уже из этого файла, и после `200` он в него не полез: те же 124 байта с тем же
временем изменения.

**Переезд в `boot_plugins.txt` снят с планов.** Он числился следующим шагом,
пока строку в `autoexec.bat` человек писал руками: `boot_plugins.txt` выглядел
аккуратнее. Теперь этой правки нет вовсе, а разница в риске осталась —
`boot_plugins.txt` грузит плагин до появления XMB, и споткнувшийся плагин
не даёт консоли подняться совсем, тогда как из `autoexec.bat` неудачная
загрузка стоит перезагрузки. Менять безопасное место на опасное ради экономии,
которой больше нет, незачем.

Кому это не нужно — `autostart = false` в `gwm.cfg`. Он же нужен при откате:
если плагин однажды уронил XMB и строку из `autoexec.bat` убрали руками,
без этого ключа следующая ручная загрузка впишет её обратно.

## Установка на консоль

1. Скопировать `gwm.sprx` в `/dev_hdd0/plugins/`.
2. Положить `/dev_hdd0/plugins/gwm.cfg` со своим токеном.
3. Загрузить плагин через webMAN на устоявшемся XMB:
   `http://<ip>/loadprx.ps3?prx=/dev_hdd0/plugins/gwm.sprx`.
4. Дальше плагин допишет себя в `/dev_hdd0/autoexec.bat` сам и будет
   подниматься при каждой загрузке консоли.

Пошагово, с проверками после каждого шага — в
[docs/INSTALL.md](INSTALL.md).

Поля `gwm.cfg` — только `token` обязателен, остальные перекрывают умолчания
из `config.h`:

| Поле | По умолчанию | Когда трогать |
|---|---|---|
| `token` | нет | всегда: без него плагин не делает ни одного запроса |
| `popups` | `true` | `false` — плагин работает молча, без уведомлений в XMB |
| `autostart` | `true` | `false` — не дописывать себя в `autoexec.bat` |
| `host` | `gowithme.club` | свой сервер или заглушка `tools/mock_ingest.py` |
| `port` | `80` | там же, где и `host` |
| `account` | имя текущего профиля | когда имя на сервере должно отличаться от локального |

В инструкции для пользователя (`docs/INSTALL.md`) остался только `token`:
`host` и `port` нужны при отладке и своём сервере, то есть тем, кто читает
этот файл.

## Приватность

Плагин отправляет только то, что нужно для статистики: title id, название, версию игры,
носитель, длительность сессии, версию прошивки и версию самого плагина. Идентификатор
консоли — соль + хеш от PSID, сам PSID/IDPS наружу не уходит. Без токена в конфиге
плагин не отправляет ничего.

Протокол приёма описан на стороне сервера —
`docs/ingest-api-v1-client.md`
в репозитории gwm-stats. Здесь, в разделе «Что уходит на сервер», записано
только то, что и почему реализовано на клиенте.
